# allw — Threat Model & Security Review Checklist

Companion to [contract.md](./contract.md), [policy-seam.md](./policy-seam.md), and
[architecture.md](./architecture.md). This document names what the approval primitive is defending,
what its invariants are expected to prove, and what reviewers should check before merging security-relevant
changes.

## Scope

This model covers the v1 approval primitive and the policy seam around it:

- `ActionRecord` capture by an integrator.
- `ApprovalContext` construction, encryption, rendering, and WYSIWYS hashing.
- Relay routing over opaque `ApprovalRequest` envelopes.
- Device-side approval signing and `device_cert` validation.
- The cross-device `device_cert` issuance ceremony (#175) — how a non-root-holding device gets certified without
  the relay being able to inject a device _signing_ key. **Specified, not built:** the relay courier is #199, and
  today certs are minted by the root holder directly. It never covered encryption recipients: integrators encrypt
  to the device list the relay serves (`GET /{acct}/devices`), which no root signature vouches for, so a malicious
  relay can still inject a recipient key (#243; see the Adversary / Asset Matrix).
- Integrator-side verdict verification, nonce tracking, policy composition, and audit records.

Out of scope:

- Preventing an agent from leaking non-secret working data it legitimately needs to read.
- Full semantic policy inference (the T3 capability engine in [policy-seam.md](./policy-seam.md)).
- Endpoint authentication details that are deferred to the enrollment mini-spec.
- Mobile OS compromise, kernel compromise, or a compromised hardware-backed keystore.

## Security Goals

1. A relay, network observer, or unrelated device must not learn the plaintext approval context.
2. A verdict must be accepted only when it was signed by an enrolled approver device for this exact request.
3. The human must be shown the exact action material that is later authorized or denied.
4. A requester origin must be attestable to the approver before approval.
5. The primitive must compose monotonically with local policy and upstream gates; it must not grant authority by
   itself.
6. Every ambiguous, expired, missing, unverifiable, or transport-failed path must block the gated action.
7. Auditors must be able to reconstruct the decision artifact and the policy state without trusting the relay.
8. The relay must never observe action **data** (arguments, values, env) — only action **structure** (program /
   server+tool / session-label / surface). "Know the function, not the arguments." This holds at every privacy
   tier.

## Trust Boundaries

```
actor/integrator process
  builds ApprovalContext, encrypts, verifies verdict, enforces policy
  applies privacy-preference: strips data fields from envelope before submit
  (default tier: relay sees structure only; paranoid/enterprise tier: relay sees routing metadata only)
  |
  | opaque ApprovalRequest envelope + ciphertext
  | envelope plaintext carries at most: structure (surface / program / server+tool / session-label), never data
  v
zero-knowledge relay
  routes by account/request/device ids, stores opaque envelopes and signed verdicts
  sees structure at most (surface / program / server+tool / session-label) at default tier; routing metadata only (paranoid/enterprise tier)
  |
  | ciphertext only
  v
approver device
  decrypts, verifies actor attestation, renders WYSIWYS, signs verdict
  full ActionRecord (structure + data) visible only here
```

The relay is intentionally outside the plaintext and signing trust boundary. It may route, delay, drop, replay,
or mutate relay-visible fields, but it must not be trusted to preserve confidentiality or authorize decisions.

**Web approver origin and its relay (#249):** the hosted web approver keeps the device's signing and
encryption seeds in browser storage, so **every script that runs on the approver origin is inside the signing
trust boundary**. Three controls keep that boundary small. (1) A strict Content-Security-Policy
(`docs/web-approver-deploy.md` §3.1) allows only the shipped same-origin scripts plus WebAssembly compilation, so
injected inline or third-party script cannot run, and `connect-src` limits fetch/XHR/WebSocket to the page and the
build-time list of relays, so those channels cannot carry a seed to a third-party origin. The CSP does **not** stop
script already running on the origin from leaking data by navigation, `window.open`, or WebRTC (see Residual
Risks). (2) The relay is **pinned at pairing** inside the stored
identity; a `?relay=` link cannot re-point a paired browser, so a phishing link cannot collect the device's relay
bearer token. (3) Relay URLs must be `https:` (`http:` only on loopback) in both the web approver and the SDK's
`createClient`, so bearer tokens and ciphertext never cross the network in plaintext.

**Structure vs. data boundary:** the relay (and anything off-device) may observe action **structure** — the
program name (commands) / server + tool name (MCP calls), session label, and surface kind — but never action
**data**: arguments, parameter values, environment variables, or any content the agent is operating on. For
MCP calls the (server, tool) pair is the function identity, parallel to a command's program name; both are
structure. Structure is what routing metadata legitimately needs; data belongs exclusively inside the JWE
ciphertext, visible only to the approver's enrolled devices. This boundary is enforced on-device (in the
WASM/native client) before anything reaches the relay.

**Privacy preference tiers (v1: default only):**

| Tier                                         | Relay sees                                                        | v1 status           |
| -------------------------------------------- | ----------------------------------------------------------------- | ------------------- |
| **default** (structure-visible)              | program / server+tool / session-label / surface kind — never data | **shipped**         |
| **paranoid / enterprise** (structure-hidden) | routing metadata only (account id, request id, device ids)        | reserved; not built |
| **ai-summary**                               | future tier — reserved; do not build                              | reserved; not built |

The preference is a RESERVED field on the wire contract (null = default in v1); see `docs/contract.md`.
Paranoid/enterprise tier — how an org enforces structure-hidden mode on its members — is an open question
tracked in the roadmap epic.

### Work-stream origin: machine verified, stream asserted

The origin shown in the inbox is a **work-stream label** with two trust weights (Decisions 4 + 5, #133; full
model in `docs/enrollment.md` §Work-Stream Attestation):

- **Which machine** is **cryptographically verified.** The machine's Secure-Enclave keypair _is_ the actor key
  of #16, anchored as an `actors` entry in root-signed account state. The per-request machine attestation
  (`allw-actor-attest+jws`, bound to `request_id` + `request_hash`) is verified on the approver device; a
  relay-supplied key never drives a verified machine identity. This sits inside the same trust boundary as the
  actor-key attestation — nothing new is trusted.
- **Which stream** is **asserted, not verified.** The harness/stream components are anchored to a deterministic
  session-ID from a **keyless** harness hook. The hook holds no key (it is a dumb emitter; crypto lives in the
  client downstream, never the hook — Security Goal 6 / fail-closed and `docs/architecture.md`). A signature by
  the verified machine over the session-ID proves only that the machine forwarded the string, not that the
  harness authenticated the session. The honest ceiling: the stream is only as trustworthy as the verified
  machine's own software stack.

**Presentation boundary (fail-closed).** The inbox MUST render the machine component with the existing
`✓ VERIFIED` / `⚠ UNVERIFIED` discipline and MUST render the harness/stream components as **asserted** — a
visibly weaker marker that is never `✓ VERIFIED`. A verified machine does not elevate an asserted stream; an
unverified machine makes the whole label unverified. This mirrors the actor-key `✓ VERIFIED` vs `⚠ UNVERIFIED`
rule (`crates/allw-core/src/attestation.rs`, `packages/approver/src/lib/render.ts`) and never renders an
asserted-only signal as cryptographically verified.

## Security Requirements

### R1. Context confidentiality

`ApprovalContext` plaintext must cross the relay boundary only as JWE ciphertext encrypted to enrolled approver
device keys. Push payloads may carry a wakeup and request id, never action context; Web Push wakeups carry no
payload at all (`docs/relay-api.md` §5). See also R7
(structure-not-data) which further constrains what the plaintext `ApprovalRequest` envelope may reveal.

Validation:

- Relay tests assert accepted envelopes contain only contract routing fields plus `context_ciphertext`.
- Pairing and relay-client tests assert no seeds or private key material are sent to the relay.
- Manual review checks any new relay field for plaintext context leakage.
- The SDK filters the relay-listed device set against the caller's verified account-state revocations
  (`revoked_device_ids`, core/WASM) before building the JWE recipient set, so a revoked device is never
  added as a recipient regardless of whether the relay's own registry has converged (`docs/enrollment.md`
  §Device Revocation, issue #204 fix 1). Tests assert a revoked device receives no recipient entry, that a
  stale lower-sequence account state cannot resurrect a revocation, and that an all-revoked account fails
  closed rather than submitting to nobody. **This holds only when the caller passes `accountStates`, and no
  shipped integrator (`@allw/hook`, `@allw/codex-hook`,
  `@allw/openclaw-bridge`) does yet**; without it the filter is a no-op and the
  recipient set is whatever the relay lists. Owner: #243.
- Recipient keys come from the relay's device registry, so a small-order X25519 key (whose ECDH shared
  secret is non-contributory and so predictable) is a runtime input, not a bug. `encrypt_context` returns
  `EncryptError::LowOrderRecipientKey` naming the device instead of panicking, and refuses the whole
  encryption rather than dropping that recipient. The SDK rethrows it, so the hook denies. The core also
  exports its denylist (`X25519_SMALL_ORDER_POINTS`, libsodium's `has_small_order` list, matched with bit 255
  masked) through WASM. The relay's `POST /pairing/complete` uses it to refuse such a device key with a 400
  before the pairing code is consumed, so the key never enters the device registry (`docs/relay-api.md` §3
  Pairing). A shared vector (`crates/allw-core/tests/fixtures/x25519_small_order.json`) asserts that the
  denylist and encryption agree in Rust and through WASM. The relay's tests drive every vector point, and
  its bit-255 variant, through pairing (#248).
  - Encryption still refuses such a key, so it fails closed whichever way the key arrives: a hostile
    relay that skips the check, a device enrolled before it, or a key from verified account state.
- Relay-chosen text (device ids, error bodies, any response body) can reach SDK error messages, and the hooks
  put those messages in the deny reason the agent reads. A hostile relay could therefore pose as an allw
  diagnostic (prompt injection). The defence is layered:
  - **The hooks are the choke point.** Both `decide()`s pass the error text through the core's
    `escape_for_display` and cap it at 256 characters (`agentSafeErrorText` in `@allw/hook`), so no SDK path,
    present or future, can put raw relay text into the agent's context. If the escape fails, the text is
    withheld.
  - **The SDK keeps relay text out of its messages.** A rejected `submit` reports only the HTTP status, not
    the relay's `error` field. A body that isn't JSON reports only the call and status, not the parser's
    message (which quotes the body). A relay device entry whose `device_id` doesn't match
    `^[A-Za-z0-9_-]{1,64}$`, or whose `pubkey` isn't a string, fails the whole call closed, and the error
    names only the entry's index.
  - **The core renders device ids escaped and capped.** `EncryptError` shows a device id with `{:?}`, capped
    at 64 characters, while the variant keeps the full id.

### R2. Verdict authenticity and binding

An integrator must accept an approval only when the verdict signature chains to the configured account root, the
verdict `request_id` equals the envelope id, the verdict `request_hash` equals the locally computed WYSIWYS hash,
the decision is `approved`, the decision is fresh, and the verdict nonce is unseen.

Validation:

- Core/WASM tests cover tampered JWS claims, mismatched request hashes, expired windows, and replayed nonces.
- SDK tests cover `verify()` returning true only for fully verified approvals.
- Integrator tests cover fail-closed behavior when verification throws or resolves non-approved.
- The relay records only provenance-valid verdicts (#245): before a verdict can become final, the core's
  `verify_verdict_provenance` checks, without plaintext, that `decided_at` lies in the request's
  `[created_at, expires_at]` (before the certificate is judged at it), the device certificate against the bound
  root, revocation in the verified account state, the JWS under the certified key, the signed `request_id`, and
  that the signer is the socket's own device. Relay tests cover junk, an uncertified key, a foreign root, a
  replayed `request_id`, another device's `kid` or `approver`, a revoked device, an expired certificate, a
  decision after `expires_at`, and an expired-certificate device backdating its decision to before the request,
  each leaving the request pending and answerable. It does not replace the integrator's verification.
- A verified non-approval is classified only from the structured WASM error (`kind: "not_approved"`, with the
  signed `decision`), never from the message. A relay controls text echoed into parse errors (#311). The shared
  vector (`crates/allw-core/tests/fixtures/wasm_vector.json`) carries signed and forged non-approvals. SDK and hook
  tests pin that a forged outer decision resolves a synthesized `denied` and that both hooks deny.

### R3. WYSIWYS completeness

The approver UI must render all material fields that are included in the request hash and relevant to the human
decision. A summary may help readability, but it is not a substitute for rendering the action substrate.

Rendering must also be **display-safe**: every context string is attacker-influenced, and a control or bidi
character can make the screen show something other than the bytes the hash binds. A command whose JSON carries
`ESC [2K` + `CR` erases and repaints its own terminal line, so `rm -rf ~/x; : <ESC>[2K<CR>git status` shows as
`git status` while the verdict binds the real bytes. In a browser, bidi overrides (U+202E, Trojan Source /
CVE-2021-42574) reorder text and zero-width characters hide it. How untrusted text reaches the human is therefore a
trust decision, and it lives in the core:

- `allw_core::display` (`crates/allw-core/src/display.rs`) defines the escaped set: C0 controls, DEL, C1 controls,
  bidi controls (U+061C, U+200E/F, U+202A–U+202E, U+2066–U+2069), zero-width and invisible characters (U+200B–U+200D,
  U+2060, U+FEFF), the rest of Unicode `Default_Ignorable_Code_Point`, U+2028/U+2029, U+FFF9–U+FFFB, and U+2800
  BRAILLE PATTERN BLANK. Notation: `\t`, `\n`, `\r`, `\xHH` for other C0 controls and DEL (ESC → `\x1b`), and
  `⟨U+XXXX⟩` for everything else.
- Variation selectors are escaped unless they follow a base their range defines variants for, because each one
  can carry a hidden byte ("emoji smuggling"): one selector after every bullet or em dash of a message would
  exfiltrate a secret, and `main` + U+FE0F looks like `main`. Shown as-is only: U+FE0E/U+FE0F after a non-ASCII base
  listed in Unicode `emoji-variation-sequences.txt` (Emoji 17.0) or as the U+FE0F of an ASCII `0`–`9`/`#`/`*`
  keycap followed by U+20E3; U+E0100–U+E01EF after a `Unified_Ideograph`; U+180B–U+180D/U+180F after a
  Mongolian-block character. U+FE00–U+FE0D and every other selector are escaped and set the flag. **Accepted
  residual:** a shown selector still carries about 1 bit per listed emoji and up to about one byte per CJK ideograph
  (240 ideographic selectors), so a payload can still ride on a run of emoji or CJK text. Ordinary prose can no
  longer carry one. This is a deliberate trade-off against warning on every emoji and CJK variant form.
  A selector after any combining mark (`Mn`/`Me`) is escaped too, whatever the base before the mark.
- Stacked combining marks are capped (#271). In a run of consecutive `Mn`/`Me` code points (Unicode 17.0.0
  `DerivedGeneralCategory`), the first two are shown as-is and the third and later are escaped as `⟨U+XXXX⟩` and set
  the flag. The run is counted over the input: an escaped character (e.g. U+034F) does not end it. Without the cap, a
  "zalgo" stack renders as a smear that can bleed over the lines above it, or hide a payload of marks behind one
  letter. **Version skew fails closed:** a renderer may know a newer Unicode than the core's tables, so a code point
  unassigned (`Cn`) in 17.0.0 counts toward a run, and a mark added later cannot extend one unflagged. The tables are
  generated by `scripts/gen-unicode-tables.mjs`, and the SDK's display-vector test checks every mark its runtime's
  ICU knows. Accented Latin, Vietnamese (NFC or NFD), Thai, Lao, Khmer, ordinary Hindi and vocalized Arabic stay
  within two marks and do not warn. **Accepted false positives:** ordinary spelling in some scripts puts three marks
  on one letter, and those words warn and show the third mark escaped: Tibetan (a subjoined stack with a vowel, so
  most Tibetan prose; `སྐྱེས`), Burmese (`မြို့`), pointed Hebrew (the points alone, as in `הַשָּׁמַיִם`, and more
  with cantillation), Quranic Arabic (`ٱللَّٰهِ`), polytonic Greek in NFD, and rarely Hindi (`फ़ूँ`). This fails
  safe, since every code point stays visible, at a warning-fatigue cost for those scripts.
- `raw` is multi-line content (a heredoc command, a file edit). In its `raw_lines` rendering a line feed is
  structure and a TAB shows as `→   `, without setting the flag: once ESC and lone CRs are escaped, a TAB or a line
  feed cannot overwrite or hide anything, and a warning on every Go edit or heredoc commit would teach humans to
  ignore it. A CR directly before a line feed is structure **only in a file edit** (shown as `␍`, unflagged), where
  CRLF endings are ordinary content. On every other surface `raw` is executed, and there a CR before LF is data that
  changes behaviour: bash reads `cd ../scratch` + CR + LF + `rm -rf -- *` as a `cd` to `../scratch` + CR, which
  fails, and then runs the `rm` in the original directory. So outside file edits that CR is escaped as `\r` and sets
  the flag. In single-line fields (argv tokens, `bin`, flags, `cwd`, ids, the summary) TAB, LF and CR are escaped and
  set the flag.
- The structure markers are not injective: literal `→   ` text displays like a TAB, and a file-edit line ending in a
  literal `␍` displays like a CRLF ending, and neither sets the flag (unlike `\x1b`, which is always paired with
  it). This is accepted: neither substitution changes what the content does in a way the human could be misled
  about, and the hash binds the real bytes.
- `display_model(context)` returns every string a surface shows (summary, actor id/kind/label, every syntactic
  substrate field, params as JSON, chain) already escaped, plus `has_hidden_or_control_chars`. It is exported through
  WASM (`display_model`, `escape_for_display`) and UniFFI (`display_model_json`, `escape_for_display`).
- Surfaces print only that model and never escape anything themselves. Layout (which field is the headline, argv
  quoting, the `raw`/`argv` divergence line) stays surface code, but layout _decisions_ such as divergence are taken
  on the raw bytes, because distinct inputs can escape to the same text (a literal `\x1b` vs a real ESC). When the
  flag is set the surface shows a warning (CLI: a line under the header, and again as the last line before the
  prompt; web: a badge on the card). The CLI ends every request block with a one-line escaped `Deciding on:` headline
  directly above the prompt, so the action and the warning are on screen when the human answers, however long the
  block is. When `raw` and the hash-bound argv diverge, `Deciding on:` shows the argv form and a "raw and argv
  differ" warning is the last line before the prompt, so the decision point never shows only the benign half. A
  multi-line command prints its further lines behind a `│` marker. The CLI also hard-wraps every row that can carry
  untrusted text to the terminal width (80 columns when stdout is not a TTY), with a `↪` marker on every wrapped row.
  Spaces are printable and never escaped, so without this a padded field would soft-wrap its tail onto a row of its
  own, where it could pose as a field label or a forged `✓ VERIFIED` origin row.
- **The web approver shows every hash-bound field the CLI shows.** Its view model carries the core's whole display
  substrate rather than a per-surface subset, so the card lists every present field whatever the surface (`bin`,
  `argv`, `flags`, `positionals`, `cwd`, `host`, `env_refs`, `server :: tool`, `params`, a file edit's
  `operation`/`paths`/`diff_summary`/`diff_hash`/content, and `raw`), plus the chain and the context summary. The
  summary is labelled as the agent's description and sits below the action heading. Whenever the hidden-character
  badge shows, the escaped character is visible on the card. When `raw` and the hash-bound argv diverge, the card
  heading is the argv form and a "raw and argv differ" alert shows, as on the CLI; the two approvers decide divergence
  with the same rule, tested against one shared fixture. The card heading uses the CLI's headline precedence whatever
  the surface (a file edit's summary, then `raw`, then the reconstructed argv, then `server :: tool`), so a record
  that mixes substrates (a tool call that also carries `argv`) heads with the command on both; a second shared
  fixture covers it.
- **Nothing on the web card or the audit receipt is clipped at any width.** Every value wraps
  (`overflow-wrap: anywhere`) and nothing is hidden behind `overflow: hidden` or a sideways scroll. The card's grid
  track is `minmax(0, 1fr)`, and the receipt's detail pane sets `min-width: 0`, so one long token cannot widen the page
  past the viewport. The hidden-character badge is the card's first line, above the action. In
  the exact plaintext (card and audit receipt), each logical line has a hanging indent, so a wrapped row of a long or
  padded value starts indented and never in the label column, the web analogue of the CLI's `↪`. A headless-Chrome
  test renders hostile cards and a hostile receipt at 360 px and checks that every tail is laid out inside the
  viewport. One layout
  difference remains: the web shows tool-call `params` as indented JSON lines, while the CLI prints compact JSON on
  one wrapped row. Pretty-printed continuation lines are always indented, quoted, or a bracket, so none can pose as a
  label.
- Neither approver shows the hash-bound `action.risk`, `capabilities` or `scope` (both show the context `risk`). The
  device now refuses a context that sets `capabilities` or `scope`, or whose shown `risk` is lower than `action.risk`
  ([contract.md](./contract.md) §Device-side context checks, #296). The remaining residual is a context that
  **raises** the risk: the human sees the higher tier but not the record's own. Owner: #340.
- Relay-supplied text outside the context goes through `escape_for_display` too. The CLI approver escapes every
  `watch` log line (request ids, relay error strings, which could otherwise repaint the request block mid-prompt),
  every `pair` output line (the relay-issued pairing code and `device_id`), and the fatal error line (which can embed
  a relay HTTP error body); if the core cannot load, the fatal error text is withheld rather than printed raw. The
  web approver escapes the verification-failed reason (which can name the relay-supplied envelope id), the
  relay-outage banner text, the ignored `?relay=` link in the relay-pin notice (#307), and the rejected pin on the
  re-pair screen (#297); a runtime without the core escape withholds that text, and the notice and re-pair screen
  withhold theirs when the core cannot load, or has not loaded within `DISPLAY_ESCAPE_LOAD_TIMEOUT_MS` (#308).
- Escaping is display-only. `request_hash` is computed over the original context; the display model is a separate
  value that is never hashed, signed, or sent.

Validation:

- Approver render tests cover command `argv`, flags, cwd, env refs, MCP server/tool/params, divergent raw/parsed
  forms, risk, actor, expiry, and challenge state.
- Any new `ActionRecord` syntactic field must either render directly or be explicitly marked non-decision-making.
- A new syntactic field must also be added to `DisplaySubstrate` so it is escaped before any surface can show it.
- The shared vector `crates/allw-core/tests/fixtures/display_vector.json` (asserted by the Rust core and through
  WASM) covers each escaped class, a mixed string, a variation-selector run, a selector after ASCII or after
  ordinary non-ASCII text (bullet, em dash, NBSP, Cyrillic, a Thai mark, an emoji with no variation sequence), and
  the allowed emoji, keycap and CJK variation forms, and stacked combining marks (a zalgo run, accented and
  Vietnamese text that does not warn, a run reset by a new base, a selector after a mark). CLI tests assert the `watch` process's stdout/stderr bytes contain no raw
  ESC/CR for the spoof above and that the warning is the line directly above the prompt, that the `pair` process
  escapes relay-supplied text, and that Go edits and heredoc commits do not warn while ESC/CR spoofs still do. Web
  tests assert a U+202E payload, an escaped envelope id and an escaped outage banner reach the DOM, with the warning
  badge present when flagged.

### R4. Fail-closed execution

Every integration boundary must deny on parse errors, missing config, network timeout, network refusal, malformed
relay responses, expired requests, non-approved verdicts, and unexpected internal errors.

Validation:

- Hook subprocess UATs spawn the real `allw-hook` process, feed gated stdin, and assert bounded `deny`.
- SDK fetch-timeout tests prove hung `fetchDevices`, `submit`, and polling resolve non-approved.
- Relay tests prove expired requests cannot become approved.

### R5. Monotonic policy composition

Policy may reduce prompts, but it must not turn a failed primitive verification into an allow. A signed
`PolicyRule` can auto-allow only before the primitive is invoked; a one-shot verdict never carries reusable scope.

Validation:

- Policy tests must pin precedence: `deny > ask > allow`; no match means ask.
- A `from_approval` rule test must prove future matching actions use a signed rule, not a reused verdict.
- Policy-rule verification tests must reject cross-account certs, signing keys that do not chain to the account root,
  missing certs, and `kid` values that do not name the certified device.

### R6. Auditability

Security-relevant decisions must leave enough evidence to verify the original request, the verdict, the policy
decision, and the previous audit chain head without trusting the relay.

Validation:

- Audit hash tests cover `prev_hash`, verdict JWS inclusion, policy block inclusion, and deterministic encoding.
- Manual review checks new decision paths append or preserve the audit evidence needed to reconstruct the gate.

### R7. Structure-not-data (relay data boundary)

The plaintext `ApprovalRequest` envelope submitted to the relay must carry **at most** action structure — the
surface kind, program name (commands) / server + tool name (MCP calls), and session label — and **never**
action data: arguments, parameter values, environment variable names or values, or any content the agent is
operating on. Full `ActionRecord` data travels exclusively inside the JWE ciphertext (`context_ciphertext`),
visible only to enrolled approver devices.

This is enforced on-device (in the WASM/native client) before any bytes reach the relay. The preferred privacy
tier is carried as a RESERVED wire field (null = default / structure-visible in v1). The three tiers are defined
in the Trust Boundaries section above; only the default tier is implemented in v1.

Validation:

- Relay envelope acceptance tests assert that no argument, parameter value, environment variable, or action-data
  key appears in the plaintext `ApprovalRequest` fields accepted by the relay.
- SDK/hook integration tests assert that the constructed envelope contains only structure fields in plaintext.
- Manual review checks every new `ActionRecord` syntactic field addition: data fields must land only inside the
  JWE; structure fields (surface, program name / server+tool name, session-label) may appear in the plaintext
  envelope.
- Any code path that serializes an `ActionRecord` toward the relay is audited for argument/value/env leakage.

### R8. Enrollment-ceremony integrity (cross-device `device_cert` issuance)

The account root must sign a `device_cert` **only** over a signing key that reached it through a channel the
relay cannot influence. Full ceremony: `docs/enrollment.md` §Cross-Device `device_cert` Issuance Ceremony.

**Status: specified, not built.** The relay courier routes are #199 (`docs/relay-api.md` §3), so the rules below
bind the implementation when it lands; today the account-root holder mints `device_cert`s directly.

Rules:

- The `enrollment_secret` that keys the CSR MAC travels **only** out of band (QR or pasted link) and must never
  appear in any request to the relay, any log, or any persisted record after the ceremony ends.
- The root holder MUST verify `csr_mac` before reading any CSR field as trustworthy, and MUST abort — never
  degrade to a weaker check — when it fails. Everything the root vouches for (`signing_pubkey`,
  `encryption_pubkey`, `device_id`) must come from the MAC-authenticated CSR, never from `GET /devices`.
- The confirmation code is derived independently on both sides and is **never transmitted**; a relay-supplied
  code would let a substituting relay replay the genuine value. It is defense-in-depth, not the primary control
  — its ~20-bit space is grindable by an adversary who already holds the secret and has seen the CSR.
- The enrollee MUST verify the returned cert against the **pinned** account-root pubkey (signature, `typ`,
  `kid`, `account_id`, `device_id`, `device_pubkey` == its own signing key, `expires_at`) **before** persisting
  it, and MUST discard-and-self-revoke on any failure.
- A device signing key is generated on-device and never exported; a provisioning bundle carrying a device
  signing seed is prohibited in all builds.
- The relay never validates the MAC or the cert; its shape/ownership checks are anti-abuse only, and a device
  may deposit a CSR only for the `device_id` its own bearer token authenticates.
- Every mailbox is write-once and TTL-bounded; abort is terminal and visible to the enrollee so a killed
  ceremony never degrades into an ambiguous timeout.

Validation:

- Core/WASM tests cover MAC verification, cross-surface byte-identical confirmation-code derivation, and every
  rejection branch (tampered pubkeys, wrong secret, wrong enrollment/account id, expired window).
- Relay tests cover write-once mailboxes (`409`), TTL expiry (`410`), cross-device CSR deposit (`403`), post-abort
  operations, and assert that no request body carrying an `enrollment_secret` is ever accepted or stored.
- Approver-surface UATs prove the inbox is unreachable without a root-verified cert, and that a forged or
  mismatched cert is discarded rather than persisted.

## Security Review Checklist

Use this checklist for PRs that touch crypto, key material, relay routing, approval rendering, policy rules,
attestation, audit records, hook/SDK fail-closed behavior, or enrollment.

### Crypto and Encoding

- [ ] New signed or hashed bytes have a domain tag and version.
- [ ] JSON that participates in hashes uses the documented canonicalization.
- [ ] Binary fields are base64url-unpadded unless the contract explicitly says compact JWS/JWE.
- [ ] JWS payload claims are cross-checked against any decoded outer convenience fields.
- [ ] Randomness is fresh per verdict/request where required; nonces are never reused.
- [ ] Low-order/invalid key material and malformed JOSE inputs fail closed.

### Key Handling and Enrollment

- [ ] Private keys, seeds, and plaintext secrets never cross the relay boundary.
- [ ] Device keys chain to the configured account root before their verdicts/rules are trusted.
- [ ] Revoked or unenrolled devices cannot resolve pending requests.
- [ ] Lost-device, rotation, and recovery behavior is either implemented or explicitly deferred to the enrollment spec.
- [ ] Test fixtures do not normalize unsafe key handling into production code.
- [ ] Cross-device cert issuance (R8): the `enrollment_secret` never reaches the relay, a log, or persistent
      storage; the root holder verifies `csr_mac` before trusting any CSR field and aborts on failure; the
      enrollee verifies the returned cert against its **pinned** root and its **own** signing pubkey before
      persisting; mailboxes are write-once and TTL-bounded; abort is terminal and visible.
- [ ] No code path ships a device **signing seed** off-device (a pre-issued `device_cert` is dev-only; a
      pre-issued seed is never acceptable).

### Relay and Transport

- [ ] Relay-visible request fields are limited to the envelope contract; no plaintext action context is added.
- [ ] The plaintext envelope carries **at most** action structure (surface / program name / session label); no
      argument, parameter value, environment variable, or other action data appears in plaintext relay-visible fields
      (R7 / structure-not-data boundary).
- [ ] Any new `ActionRecord` syntactic field is classified: structure fields may appear in the plaintext envelope;
      data fields must land exclusively inside the JWE `context_ciphertext`.
- [ ] Push/wakeup payloads carry request ids only, never human-shown context.
- [ ] Any outbound request whose target a client supplies is constrained to an allowlist (SSRF). Web Push
      subscription endpoints must be `https:` on known push-service hosts, are re-checked before every send, and
      redirects are not followed (`docs/relay-api.md` §5).
- [ ] Anything a client registers that costs outbound work on every submit (push tokens) is budgeted per
      registration and per account (over budget is rejected, not truncated), and that work runs off the response
      path with per-request timeouts, so it can neither stall nor fail a submit (`docs/relay-api.md` §3, §5).
      Outbound pushes triggered by unauthenticated callers are coalesced per subscription (`WEB_PUSH_COALESCE_MS`).
- [ ] Pending requests expire fail-closed; expired requests cannot later resolve approved.
- [ ] A device verdict becomes final only after the core's provenance check against the request's window, the
      bound root and verified account state, signed by the socket's own device; a refused verdict records nothing
      and retracts nothing
      (`docs/relay-api.md` §4, #245).
- [ ] Network failures, hung reads, refused connections, and malformed relay responses deny or expire, never allow.
- [ ] Any new endpoint states who may call it and what authentication/authorization is required.
- [ ] Relay URLs are accepted only as `https:` (or `http:` on loopback) and are rejected at configuration time,
      before any request is built (web approver `checkRelayUrl`, SDK `assertRelayUrlTransport`, approver CLI
      `assertCliRelayUrl` for `pair --relay`, `watch --relay` and the keyfile's `relay_url`). Every copy of the rule
      is tested against `packages/sdk/test/fixtures/relay-url-vectors.json`.
- [ ] A paired web approver talks only to the relay pinned in its stored identity; no query parameter, link, or
      other page input can re-point it without re-pairing.
- [ ] Web approver changes keep the `_headers` CSP intact: no inline script or `'unsafe-inline'`, and
      `connect-src` lists only the page and the build-time relay origins.

### WYSIWYS and Approver UX

- [ ] Every field covered by `request_hash` that matters to the decision is rendered or intentionally explained.
- [ ] Every untrusted string reaches the screen through the core display model (`display_model` /
      `escape_for_display`); no surface prints a raw context, envelope, or relay string or escapes on its own (R3).
- [ ] Control, bidi, and zero-width characters render as visible escapes, and the surface shows its
      hidden-character warning whenever `has_hidden_or_control_chars` is set.
- [ ] Display escaping never feeds `request_hash`; layout decisions (e.g. raw/argv divergence) compare raw bytes,
      not escaped text.
- [ ] Parsed and raw command/MCP forms cannot diverge silently.
- [ ] Expiry, actor identity, risk, reversible status, and challenge requirement are visible before signing.
- [ ] Unverified actor identity is not presented as verified.
- [ ] Work-stream label (#133): the **machine** component is `✓ VERIFIED` only on a verified machine attestation;
      the **harness/stream** components are rendered **asserted**, never `✓ VERIFIED`, and a verified machine does
      not elevate an asserted stream (fail-closed presentation — `docs/enrollment.md` §Work-Stream Attestation).
- [ ] Approve/deny/skip behavior preserves fail-closed semantics.

### Integrator, Policy, and Audit

- [ ] The integrator computes `allow` only after verified approval plus local policy plus other gates.
- [ ] A non-approved, expired, unverifiable, replayed, or transport-synthesized verdict cannot become allow.
- [ ] Policy precedence remains `deny > ask > allow`; no match remains ask.
- [ ] `from_approval` emits a signed `PolicyRule`; it does not mutate or reuse the one-shot verdict.
- [ ] Audit records contain the verdict artifact, request hash, actor, action, policy result, and previous hash.
- [ ] New config has fail-closed validation and cannot weaken timeout-ordering or verification guarantees.
- [ ] Integrator trust-anchor config (`~/.allw/config.json` + `ALLW_*` overrides) is read only through `loadClientConfig`; it never holds secrets, and the account-id/root-key consistency check goes through the core.
- [ ] The config path is absolute however it is reached (`ALLW_CONFIG`, the path option, or the `HOME`-based default), and
      loader errors, which the hooks hand the agent as deny reasons, never echo file content: no values, no key
      names, no rejected `relay_url` (#301).

## Review Evidence To Include In PRs

Security-relevant PR descriptions should name:

- which invariant(s) the change touches;
- which adversary or residual risk it changes;
- the exact tests or fixtures proving the behavior;
- any remaining deferred behavior and its owning issue/doc.
